# 昼夜权重：让基础权重跟着鱼种的昼夜习性浮动

Status: done

## Problem Statement

「钓场与鱼口」页每行的基础权重是判鱼抽签的唯一依据：同一条鱼全天 24 小时权重不变，
玩家在夜里钓不到夜行鱼不是因为夜里它们更活跃，只是运气。文章《俄罗斯钓鱼4 系统玩法深度拆解》
把「每张图是独立生态、同一鱼种在不同时刻行为不同」列为生态真实感的支柱，我们这条没落地。

代码里其实已有昼夜层（`fishDielWeight`），但被两件事挡住了：

1. 它挂在 `fish_ecology_enabled` 之下，而这个开关**默认 0**。整套生态（水温/水层/天气/清澈度）
   一起关着，昼夜自然不生效，玩家看到的就只有基础权重。
2. 它本身的位映射是错的。`fishActivityForHour` 返回 晨=1/昼=2/暮=3/夜=0，却被 `1<<bit`
   当掩码位用，而掩码定义是「1 晨 2 昼 4 暮 8 夜」。结果夜里查的是「晨」位、早晨查「昼」位，
   整体错位一格。因为开关默认关，这个 bug 一直没暴露；直接把生态打开反而会让夜行鱼在夜里
   拿不到加成。

## Solution

把昼夜从生态总开关里拆出来，成为独立一层，**默认开启**：

- 该鱼种处在活跃时段（由其昼夜掩码判定）时，权重乘活跃加成；
- 不在活跃时段时乘 `fish_diel_inactive_penalty`（默认 0.30）。

**活跃加成按「专一度」分档，不是一刀切**（2026-11-17 晚修订）。第一版是全天一个 1.25，
问题是它对「纯夜行」和「早中晚三段都活跃」的鱼一视同仁：前者一整天才一个时段能吃到，
后者三个时段都在吃，用同一个倍率等于把差异化抹平了。现在按活跃段数折算：

| 活跃段数 | 加成（peak=2.0） | 含义 |
|---|---|---|
| 1 段 | ×2.00 | 纯夜行/纯日行，只在一个时段出没 |
| 2 段 | ×1.67 | 两个时段活跃 |
| 3 段 | ×1.33 | 大部分时间都活跃 |
| 4 段 | ×1.00 | 全天都有，没有时段红利 |

于是纯夜行鱼夜里 ×2.0、白天 ×0.3，约 **6.7 倍**对比；而「昼夜都活跃」的 4 段鱼
完全不受影响，不会因为开了昼夜权重就把整图鱼口重新洗一遍。

修掉位映射错位，让掩码与后台「1 晨 2 昼 4 暮 8 夜」的说明真正一致。

「全局不出鱼」（`enabled=0`）仍只属于生态总开关：昼夜层是乘子，不该让鱼凭空消失。

## User Stories

1. 作为玩家，我希望夜行鱼（如江鳕、鳗鲡）在夜里更容易上钩、白天明显变少，这样「挑时间出钓」
   才有意义，而不是全天同一个概率。
2. 作为运维，我希望默认就有昼夜差异而不用先打开整套生态（那会一次性改变水温/水层手感），
   并且能单独调加成/压制的强度。
3. 边界：昼夜开关与生态开关都关时完全中性（返回 1），与改动前一致；没有昼夜档案的鱼种
   （掩码为 0）按非活跃处理，不会因缺数据凭空加权；窝料门只吃压制面（≤1），不因加成变成 >1。

## Implementation Decisions

- `fishActivityForHour` 改为返回**位序** `uint`：0=晨 1=昼 2=暮 3=夜，直接对应 `1<<bit`。
  2026-11-17 晚进一步下沉到 `internal/worldclock.SegmentOf`：后台也要按同一套算术判断
  「现在哪个时段」，两边各写一份迟早漂移。
- `worldclock.ActiveBoost(mask, peak)`：按 popcount(mask) 折算加成，`peak<=1` 或段数
  为 0/4 时返回 1（活跃时段反而压制是反直觉的，后台填了也不采用）。
- `fishDielWeight(profile, hour, activeBoost, inactivePenalty)`：把两个倍率变成显式参数，
  不再硬编码，也不再自己读 tunable——纯函数便于单测。
- `fishBiteEnvironmentWeight`：先判 `ecologyOn` 与 `dielOn`，两者都关才返回 1；只开昼夜时
  直接返回昼夜系数，不牵连水层/水温/天气/清澈度；生态开时昼夜作为 factors 里的一层（受
  `dielOn` 控制是否加入），`enabled=0` 的归零仍只在生态开时生效。
- 窝料（`groundbaitGates`）沿用同一组倍率，但结果继续夹在 `[0.05,1]`——门不吃加成。
- tunables：`fish_diel_weight_enabled`(1)、`fish_diel_active_boost`(2.0，峰值)、
  `fish_diel_inactive_penalty`(0.3)。后台在「游戏参数 → 玩法与钓组 → 昼夜权重」，
  倍率限 0.05~3，开关限 0/1。
- 后台「钓场与鱼口」页把系数直接摆出来：每行显示活跃时段标签（当前时段描边）与
  「当前权重 = 覆盖权重 × 当前时段系数」，表头写清现在几点、峰值与非活跃倍率。
- 兼容：不改协议、不改表结构；回滚 = `fish_diel_weight_enabled=0`，行为回到改动前的全中性。

## Testing Decisions

- 单元（`internal/gameserver/fish_diel_weight_test.go`）：给定仅夜(8)/仅昼(2) 两个档案，
  断言 22 点与 12 点分别拿到加成/压制，覆盖 夜/昼/晨/暮 四段映射——这组用例在修正位映射前
  必然失败（实测：夜行鱼 22 点拿到 0.35）。
- 单元（`TestDielBoostScalesWithActiveSegments`）：1/2/3/4 段分别对应 peak、1+2(peak-1)/3、
  1+(peak-1)/3、1；并断言段数越少加成越高、纯夜行鱼夜间/白天约 6.7 倍、4 段鱼系数为 1。
- 单元（`internal/worldclock/worldclock_test.go`）：日长换算（150 真实秒 = 1 游戏小时）、
  段边界（4→夜、5→晨、9→昼、16→暮、20→夜）、负值与跨日归一、掩码标签与 popcount。
- 集成（真实 SQLite + tunables）：生态关、昼夜开时 `fishBiteEnvironmentWeight` 返回昼夜系数
  而非 1；两者都关时返回 1；生态关时 `enabled=0` 的鱼不被归零。
- 期望值来源：倍率字面量（2.0 / 0.3）与时段的日历定义，不用被测函数反算。
- 回滚后变红：把 `fish_diel_weight_enabled` 默认改回 0 时，集成用例失败；把位映射改回
  1/2/3/0 时，单元用例四条全红。

## Out of Scope

- 不引入按地图的气候/水温差异（水温仍由世界钟与天气统一推算）。
- 不改季节、水层、天气、清澈度等其余生态维度的强度，也不改它们的默认开关。
- 不做「玩家可见的昼夜提示」（如 UI 显示某鱼活跃时段），那是攻略侧的事。
- 不改基础权重本身（`base_weight` 仍是静态基准，昼夜只做乘子）。

## Further Notes

- `[事实]` 全局 `fish_ecology` 253 行里没有掩码为 0 的鱼种：2 种纯夜行(8)、198 种含夜间段，
  另有 55 种不含夜间段；因此修正位映射后，夜间与日间的候选结构会真实分开。
- `[事实]` 昼夜层此前唯一的另一个消费方是窝料门（`groundbaitGates`），它自带 `≤1` 夹取，
  加成不会外溢。
- `[推断]` 2.0 这个峰值按「专性鱼夜里翻倍」定，配 0.3 的压制得到 6.7 倍昼夜对比。
  实测觉得还不够明显时优先调 `fish_diel_active_boost`，而不是继续压低
  `fish_diel_inactive_penalty`（后者过于接近 0 会让白天几乎只剩日行鱼）。
- `[修订]` 2026-11-17 晚：加成从「一刀切 1.25」改为按活跃段数分档，峰值提到 2.0、压制降到 0.3。
  起因是玩家反馈「夜行鱼夜里该涨得更多」——原值对纯夜行鱼只有 1.25，感知不明显；
  而直接抬成全天 2.0 又会把三段/四段活跃的鱼一起抬高，等于没做差异化。
- `[事实]` 253 条档案的段数分布：1 段 2 种、2 段 96 种、3 段 120 种、4 段 35 种。
  所以分档后拿到满额 2.0 的只有 2 种纯专性鱼，大多数鱼落在 1.33~1.67，符合直觉。
