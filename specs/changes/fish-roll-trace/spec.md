# 判鱼决策追踪：把「为什么空军」变成可读的一行

Status: done

## Problem Statement

判鱼权重由名册、硬性鱼口门、区域名册、饵料规则、鱼群分布、生态环境、钓点观测、窝料、饵效
共约九层依次相乘决定，但结果只落下一行日志里的「空因」。玩家连空军时无法判断是自己选错了
点位/水层/饵，还是这一杆本来就该空；运维调参也只能靠反复实钓试。

社区复盘文章《俄罗斯钓鱼4 系统玩法深度拆解》把「失败可归因」列为长线留存的根本原因——玩家
断线/脱钩/空军之后能反推出是哪一环出了问题，才会接着优化下一套方案。我们目前在客户端物理层
（搏鱼、耐磨、脱钩）已有归因材料，判鱼层完全没有。

## Solution

每一杆真实咬钩判定在服务端留一份决策快照：这次有哪些候选鱼种、每一层乘完之后权重各是多少、
最后选中谁（或在哪一层被清空）。后台「钓场与鱼口」页新增「判鱼追踪」面板，按时间倒序展示，
可按水域筛选。查鱼助手、区域估算预览等非真实咬钩不写追踪。

## User Stories

1. 作为运维，我希望看到某次空军是被哪一层清空的（食性硬门 / 分布 / 区域名册 / 权重全零），
   以便直接定位该调哪个参数，而不是逐项开关试错。
2. 作为运维，我希望看到中鱼那次的候选 Top5 以及每层乘完的权重，以便判断「为什么是这条鱼」、
   某张图是不是被某个鱼种吃满了权重。
3. 边界：追踪关闭或表为空时面板显示空态，不报错；GM 指定下一条鱼（绕过判鱼）不写追踪；
   表按保留条数环形裁剪，超出丢最旧，不会无限增长；保留条数设 0 时不落库。

## Implementation Decisions

- 数据：新增表 `fish_roll_trace`（迁移 `00070_fish_roll_trace.sql`），一次判定一行，
  `payload` 存候选/各层权重的紧凑 JSON。插入后按 `fish_roll_trace_keep` 裁剪，保持环形。
- 采集：`fishRollContext` 新增 `trace *fishRollTrace`（nil = 不采）。采集点在
  `internal/gameserver/fishing.go` 的判鱼主链每层之后，用一个 `step(name, keys, wts)` 统一打点；
  层名固定为 `roster / gate / zone / bait / dist / ecology / spot / groundbait / bait_tier / final`。
- 持久化只有一个入口：`onBiteTimer` 真实咬钩路径。`rollFishFromDBWithRules` 仍可能被查鱼、
  区域估算、测试采样复用，因此不在这里落库。
- tunables：`fish_roll_trace_enabled`（默认 1）、`fish_roll_trace_keep`（默认 300）。
  两者为纯诊断开关，不参与任何判鱼数值。
- 管理端：`GET /api/fish/roll-trace?loc=&limit=` 只读列表，沿用现有 JWT 鉴权与审计约定
  （只读接口不写 audit_log）。
- 兼容：不改协议、不改判鱼结果、不动静态库；回滚 = 关 `fish_roll_trace_enabled`，
  表可原地保留不影响旧档升级。

## Testing Decisions

- 单元（纯逻辑，`internal/gameserver/fish_roll_trace_test.go`）：给定若干层 `keys/wts` 快照，
  断言 ①同一个 key 在不同层的权重按层序对齐；②被某层剔除的 key 在后续层记 0；
  ③Top5 按最终权重取，且并列时稳定（不因 map 遍历乱序抖动）。
- 存储（真实 SQLite）：插入 5 条、`keep=3`，断言只剩最新 3 条且删除的是最旧；
  `keep=0` 时不写库。
- 期望值来源：手算样例（权重数组字面量），不用同样代码再算一遍；存储断言用 `id` 与自增顺序。
- 回滚后变红：删表或去掉裁剪逻辑时，存储用例必然失败；关掉采集后单元用例仍绿（纯逻辑）。
- 不新增协议/实机用例：本改动对客户端零可见。

## Out of Scope

- 不把追踪暴露给玩家（不做「为什么没鱼」的玩家提示，那是另一件事）。
- 不做统计聚合、时序图表、按鱼种命中率报表。
- 不改任何判鱼数值、权重、档位或咬钩节奏。
- 不追踪查鱼助手与区域估算（避免二次计数干扰真实手感证据）。

## Further Notes

- `[事实]` 判鱼主链的九层顺序与现有代码一致，见 `internal/gameserver/fishing.go`
  `rollFishFromDBWithRules`；`emptyReason` 已存在且只进日志。
- `[推断]` 「失败可归因」能提升留存，来自社区复盘文章的定性论述，我们只把它落到运维可读，
  未做玩家侧验证。
- `[假设]` 每杆一次 insert 的写放大可忽略：单玩家咬钩频率约 30 秒一次，保留 300 行。
  若实测有压力，优先降 `fish_roll_trace_keep` 而不是加采样。
