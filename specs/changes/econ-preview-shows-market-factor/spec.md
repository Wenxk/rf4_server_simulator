# 后台试算页显示当日行情系数

Status: done

## Problem Statement

运营在「鱼种经济」页试算 `a_omul`（秋白鲑）上星档 1kg，看到：

- 配置表里「默认 银/公斤」写着 **37.86**
- 下方试算「卖价」显示 **38.65 银**

于是报障：「1 公斤不就是 1000g 吗？为什么卖价不等于每公斤价？」

**数值本身没错**，缺的是解释。卖价公式实际是：

```
卖价 = 基准价 × 水域倍率 × 当日行情系数 × (克重/1000) × 新鲜度
```

`当日行情系数 = dailyMarketFactor(species, now)`，按「UTC 日期 + 鱼种」哈希取值，
范围 **0.95–1.05**，同一鱼种当天固定、跨天变化。当天 `a_omul` 恰好是 **1.020877**，
所以 `37.86 × 1.020877 × 1kg = 38.6504 → 38.65`。

问题出在界面：试算那行只写了「按刚钓获的新鲜度」，**把行情系数隐掉了**。
页面顶部的小字虽然有「鱼价在基准价之上再叠当日系数（±5%）」，但离试算结果远，
没人会把两处联系起来，结果看起来就是「算错了」。

## Solution

把行情系数与完整算式摊在试算结果里，让数字自证。

接口 `/api/econ/preview` 新增返回 `market_factor`（当日行情系数），
试算结果显示三行：

1. `经验 … · 卖价 … 银`
2. `1000g · 3 档 · 阿赫图巴河 ×1 · 刚钓获（新鲜度 1.0）`
3. `算式：基准价 37.86 × 水域倍率 1 = 本图 37.86 银/kg，再 × 当日行情 1.0209 × 1kg → 38.65 银`
   加一行说明「当日行情取 0.95–1.05，按『UTC 日期 + 鱼种』哈希，同一鱼种当天固定、
   跨天会变；因此 1kg 通常不正好等于每公斤基准价。」

## User Stories

1. 作为运营，我希望试算页直接告诉我「为什么 1kg 卖价不是每公斤价」，而不是让我猜或翻文档。
2. 作为运维，我希望明天同一鱼种算出不同价时，界面能让我一眼看出这是日行情波动，不是有人改了价表。
3. 边界：只加展示与一个只读接口字段，不改任何结算逻辑，也不改行情系数的算法与范围。

## Implementation Decisions

- `gameserver/econ_export.go` 新增只读导出 `SpeciesDailyMarketFactor(species, now)`，
  包住已有的 `dailyMarketFactor`。不直接暴露内部函数，保持 `econ_export.go` 作为
  「后台只读查询出口」的边界。
- `admin/econ.go` 的 preview 响应加 `market_factor` 字段。其余字段（`base_price`、
  `price_per_kg`、`map_pct`）语义不变：**都是基准水域口径**，前端需要自己乘 `map_pct`。
- `admin/web/index.html` 重写试算渲染：
  - 用 `ECON_MAPS` 把地图 key 换成中文名，不露 `level_009_ahtuba` 这种内部键。
  - 算式里明确区分「基准价 → × 水域倍率 = 本图每公斤价 → × 当日行情 × 克重」，
    避免把水域倍率算两次（`marketSilverPerKgOverlay` 返回的已含倍率，但接口暴露的
    `base_price` 是基准水域价，两者口径不同，容易踩）。
- 文档 `docs/admin-console.md` 试算段补算式与「这是唯一原因」的说明。

## Testing Decisions

- 新增 `TestPreviewPriceEqualsPerKgTimesMarketFactor`：对 4 个鱼种断言
  `PreviewSpeciesEcon(…, 1000g) == round(每公斤价 × 行情系数 × 100 分)`，
  并校验系数落在 0.95–1.05。这条测试锁住「差额来自行情系数」这个事实。
- 行情系数本身的「同日稳定 / 跨日变化」已由既有 `TestDailyMarketFactorRangeAndStability`
  覆盖（用 `marketDayForced` 固定日期，比新写一份更严谨），故本次未重复添加——
  曾一度写重名测试，编译报 redeclared，已删除。
- `econ_ui_test.cjs` 夹具补 `market_factor:1.0209`，并新增三条断言：
  试算文本必须含「当日行情」「1.0209」「算式」。已验证渲染通过。
- 用真实数据（`a_omul` g3 基准 37.86）截图核对：算式 `37.86 × 1.0209 → 38.65`
  与报障截图完全一致，布局无溢出。

## Out of Scope

- **不改行情系数算法**（仍为 0.95–1.05、UTC 日期 + 鱼种哈希）。这是有意的日价波动设计，
  改它等于改经济节奏。
- **不在列表页也显示行情系数**：列表展示的是基准价，倍率与行情属于「某次成交」的口径，
  混在一起反而更乱。
- **不给试算加「按指定日期」选项**：运营试算要看的是「现在卖多少」，加日期选择器会让
  人误以为结算价可预订。需要复现某天结果时用单测的 `marketDayForced`。

## Further Notes

- [事实] 报障当天的系数：`fnv32a("20261123|a_omul") % 10000 / 9999 = 0.208895`，
  `0.95 + 0.10 × 0.208895 = 1.020877`，`37.86 × 1.020877 = 38.6504`。
- [事实] 同一鱼种换一天会变：`20261124` 的系数是 `0.995805`，1kg 只卖 37.70 银。
  所以「今天多 2%、明天少 0.4%」都是正常波动。
- [推断] 这类「展示层漏说明」比计算错误更难发现，因为数字在容差内、测试也全绿。
  凡是界面上出现「输入值 × 系数 ≠ 显示值」的地方，都应该把系数显式列出来。
- [假设] 若后续把行情做成可配置（比如活动期间放大波动），本 spec 的算式文案仍然成立，
  只需把「0.95–1.05」改成读配置。
