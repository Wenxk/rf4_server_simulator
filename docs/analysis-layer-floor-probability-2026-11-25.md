## 一、结论先行

**问题回答：超活跃水层被钓获的概率是高还是低？——分两种情况，不是同一个问题。**

| 场景 | 超层占比 | 判定 |
|---|---|---|
| **有界内合法候选**（绝大多数正常配置） | **0.126%** | 极低。约每 800 条渔获才 1 条超层，符合「现实里偶尔有杂口」的手感 |
| **无界内合法候选**（饵的 allow 名单与本水层完全不交） | **100%** | 必然超层。但这是结构性缺口，**与地板参数无关** |

**参数是否合理？——参数本身合理且行为可预测，但默认值与文档口径差 8 倍。**

- 地板是**严格线性、完全可预测**的：实测超层占比 = `f·b/(f·b + (1−b))`，其中 `b` = 不设地板时的超层基线（实测 11.21%），`f` = 地板值。全部 8 个取值点偏差 **0.0%**。
- 当前默认 `0.01` 实测只压到 **0.126%**，比后台文案写的「约 1%」**低 8 倍**。要真正得到 1%，地板应设 **0.08**。
- 若认为 0.126% 正是想要的（千分之一级别的极小杂口），那**代码是对的、文案该改**；若想按文案的 1% 执行，则**默认值该改 0.08**。**建议前者**——0.126% 更贴近「极小杂口」的设计意图。

## 二、方法：用权重向量算精确值，不靠采样猜

上一轮合规审计是「判鱼 → 数渔获」，168 次判鱼只能看到 12 条超层，样本太薄，且无法区分「地板没压住」和「压根没有界内候选」。

这一轮换成**读判鱼链的中间结果**：生产代码在每一层之后都会把完整权重向量写进 `fishRollTrace` 快照（`rollStageFinal` 就是真正参与抽签的权重）。据此可以算出

```
超层抽签概率 = Σ(超界候选 final 权重) / Σ(全部候选 final 权重)
```

这是**精确值**，不是抽样估计，因此每个 (方案, 钓层, 游戏小时) 判一次鱼就够。全天候 × 全水层 × 10 个地板值 = 1590 个探针，16 秒跑完。

`weightedChoice` 是归一化抽签（`r := rand.Float64() * total`），所以**总权重的绝对大小不影响开口率**，只影响超层鱼在抽签中的相对占比——这正是要测的量。

### 3.3 红虫·底水 12.75% 的成因：不是地板失效

单看 12.75% 会误判。逐小时拆开后：

- **21 个正常小时**：超层占比 均值 **0.291%**、中位 **0.126%**、最大 0.62% —— 与其他组合一致，地板正常工作。
- **5–7 时（游戏内「晨」段）**：3 个小时都是 **100%**，把这组均值从 0.29% 拉到 12.75%。

这 3 小时发生了什么，逐层归因给出了确切答案：

| 判鱼层 | 界内候选数 | 说明 |
|---|---|---|
| roster → gate | 14 | 名册里 14 种鱼水层合规 |
| dist（鱼群分布） | **4** | `distributionMultiplier` 把 10 种鱼归零，只剩 `crucian`/`frog`/`vjun`/`c_bleak` |
| **ecology（昼夜禁口）** | **0** | 剩下这 4 条鱼的晨段曲线值分别 0.45 / 0.25 / 0.49 / 0.16，**全部 < 0.5**，被 `fish_diel_inactive_block` 整段禁口 |

也就是说：**分布先把池子做窄，昼夜再把最后几条卡在阈值下，界内候选归零 → 只剩 `perch`（曲线晨段 0.61，唯一活跃）→ 必然中签。** 地板此时没有可作法的对象，不是它没压住。

补充：`c.roach`（晨段 0.56，本应放行）也在 `dist` 层被散布归零了，没进到昼夜判定。这是两层独立机制的叠加，不是任何单层的错。

## 五、反推：地板该设多少

设 `b` = 完全不设地板时的超层权重占比（实测 **11.21%**），`f` = 地板值，则

```
实际超层占比 = f·b / (f·b + (1−b))
```

反解得到：

| 目标超层占比 | 所需地板 `f` |
|---|---|
| 0.1%（千分之一） | **0.008** |
| 0.5% | 0.040 |
| **1.0%**（后台文案写的） | **0.080** |
| 2.0% | 0.162 |
| 5.0% | 0.417 |

对照当前 `0.01` → 实测 **0.126%**。

**这里藏着一个口径偏差，需要用户决定：**

- 后台文案（`index.html:1049`、`:2790`）写「0.01 = 保留约 1% 极小杂口」。
- 代码行为没错，`0.01` 就是乘 0.01；错的是「1%」这个说法——超层候选本身只占 11.21% 的基线，再乘 0.01 后归一化，得到的是 0.126%，不是 1%。
- 两条路：**(A) 改文案**，把「0.01=约 1%」改成「0.01=约 0.13%」；**(B) 改默认值**到 0.08 让文案成立。

**推荐 (A)。** 理由：0.126% 是「每 800 条渔获 1 条杂口」，这才是「极小杂口」该有的量级；1% 是「每 100 条 1 条」，玩家能明显感知到「水层不对也老上鱼」，反而不像刻意保留的例外。

## 六、一个必须纠正的推断

本轮中途我曾判断「面包·浅水总权重只有 0.387（正常的 0.27%），所以开口率被压到 1/365，影响可忽略」。

**这个推断是错的，已用实测推翻。** `weightedChoice` 做的是归一化抽签，总权重绝对值不参与开口率。

实测各配置命中率（`bite_legality.json`，每格 24 次判鱼）：

| 配置 | 总权重中位 | 命中率 |
|---|---|---|
| 浮钓·面包 浅 0.16 | **0.387** | **41.7%** |
| 浮钓·面包 中 0.40 | 141.0 | 54.2% |
| 浮钓·面包 底 0.93 | 204.5 | 58.3% |
| 浮钓·红虫 中 0.40 | 686.8 | 62.5% |
| 路亚·旋转亮片 | 105.8 | 83.3% |

面包·浅水总权重比红虫·中低 **1774 倍**，命中率只低 21 个百分点。**所以「被迫超层」是实打实的手感问题：玩家会稳定地上鱼，只是上的鱼全部水层不对。**

## 七、判定与建议

### 7.1 参数本身的判定：✅ 合理

| 维度 | 判定 | 依据 |
|---|---|---|
| 行为可预测性 | ✅ 优秀 | 8 个取值点零偏差，严格符合闭式公式 |
| 单调性 | ✅ 正常 | 0.001→1.0 单调递增，无拐点 |
| 0 值语义 | ✅ 正确 | `f=0` 时超层权重彻底归零（实测 0%），完全杜绝 |
| 1 值语义 | ✅ 正确 | `f=1` 等于不设地板，退化为纯生态软权重 |
| 默认值方向 | ✅ 合理 | 0.01 压到 0.126%，确实落在「极小杂口」区间 |
| 默认值文案 | ❌ **偏差 8 倍** | 文案说 1%，实测 0.126% |

### 7.2 建议动作

| 优先级 | 事项 | 说明 |
|---|---|---|
| **P1** | 改后台文案（`index.html:1049`、`:2790`） | 「0.01=保留约 1%」→「0.01=保留约 0.13%（约每 800 条 1 条）」。不改代码，只让文档与行为对齐 |
| **P2** | 面包·浅水结构性缺口 | 两种处理：①**不管**——现实中用面包在水面浮钓确实钓不到鲤鱼/鲫鱼，空竿或被迫上杂鱼都合理；②加**空竿重排**——界内候选为空时直接判空竿重来，而不是让超层鱼中签。当前已有 `bite_empty_retry_scale`（空轮重排倍率）机制，但只对「候选权重全零」生效，**不覆盖「有候选但全超层」**这种情况 |
| **P3** | 晨段叠加坑 | 红虫·底水 5–7 时 = 分布窄 + 昼夜禁口同时发生。这是两层机制独立正确、叠加后却无鱼可钓。属边缘体验问题，量级很小（3/24 小时），可不动 |

### 7.3 不建议做的事

- **不要为了让「1%」成立而把地板调到 0.08** —— 玩家会明显感觉水层判断失效。
- **不要给超层鱼加绝对下限/绝对上限** —— 当前的地板已经是这种机制，再加一层只会让行为不可预测。
- **不要动 `bite_gate_layer_floor` 的 clamp 范围**（`[0,1]`）—— 实测 0 和 1 的语义都正确。

## 八、数据可信度说明

- 全部判鱼走生产函数 `rollFishFromDBWithRules`，水层判定走 `rigWaterLayer` + `cachedFishEcology`，与线上同一套口径。
- 昼夜权重走生产的 `fishDielWeight`，鱼群分布走生产的 `applyFishDistribution`。
- 合规自检不自己重算生态：超界判定直接读 `LayerMin/LayerMax` 与 `biteGateLayerTol`（0.15），与实际裁剪逻辑同源。
- 交叉验证：用 trace 的 `roster→gate` 权重比值反推「哪些鱼被地板裁过」，与自算判定**完全一致**。
- 时间注入：`now` 按游戏日零点 + hr 游戏小时构造，覆盖 24 个游戏小时真实昼夜/分布相位。
- 本轮修复了一个测试污染：首版 cleanup 在原值缺失时会留下 `value=""` 脏行，导致下一轮 `bite_gate_layer_floor=1` 被固化。已改为「原本不存在则删除该行」，并已修复被污染的快照库（`data/playtest/fresh.db` 现只剩 `bite_gate_enabled=1`，与原状一致）。
