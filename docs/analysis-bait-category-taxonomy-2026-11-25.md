# 饵料分类体系：以静态库实测数据为准

> 本文是「吃饵规则编辑器层级选择」的唯一事实源。所有数字都从
> `server_data/static.sqlite3` 现查得到，不含推断。
> 复核命令见文末「复现方式」。

## 0. 为什么要重做

此前 `bait_type_terms.go` 的天然饵词表里有 `虫类`(2)、`蚯蚓类`(6)、`昆虫类`(7)
三个词。这三个是**代码自造词，游戏中不存在**：

- 游戏里叫 `幼虫`、`蠕虫`、`昆虫`；
- 游戏里还有 `自然的`、`活的`、`小型甲壳类`、`粥和面团`、`下沉香煮成饵`、
  `Pop-up 香煮成饵`、`小药`、`套装` 这些代码里压根没有的概念；
- 反过来，代码里的 `虫类` 把 `幼虫` 和别的混在一起，`蚯蚓类` 把 `蠕虫` 改了名。

结果是：后台能选到的词和玩家在游戏里看到的分类对不上。

## 1. 分类字段：只有两个，且互斥

饵料分类**全部**来自 `item_def`：

| 字段 | 含义 | 覆盖 | 取值数 |
|---|---|---|---|
| `category` | 大类：17 拟饵 / 27 天然饵 | 4123 款 | 2 |
| `attrs_json.mbemakijdeh` | **拟饵**类型 lureType | 3178 款（cat=17 全部） | 20 |
| `attrs_json.fopbhlmkcpe` | **天然饵**类型 baitType | 945 款（cat=27 全部） | 16 |

实测：`category=17` 的 3178 款**全部**有 `mbemakijdeh`、**全部**没有 `fopbhlmkcpe`；
`category=27` 的 945 款**全部**有 `fopbhlmkcpe`、**全部**没有 `mbemakijdeh`。
两者严格互斥，不存在交叉。

> 注意：`fopbhlmkcpe` 这个键名在别的表里表示别的枚举（如装备类型、
> 鱼动作行为组）。只在 `item_def.attrs_json` 里、且 `category=27` 时才是 baitType。
> 这是既有的命名冲突，不要跨表套用。

已排除的候选字段（都不承担分类语义）：

- `gkfbafmbpam`（规格号 1/2/3，7 个取值，全库 4123 款都有）——是重量档，不是分类；
- `kind`——是**品牌名**（`zeiman` / `sorvik` / `heaven_creek` / `Handmade`…），
  拟饵 28 个品牌、天然饵 8 个；
- `brand`——是**产品系列**（`zmn_spiker2` / `svk_storfisk_l33_450`…），
  拟饵 366 个系列、天然饵 239 个；
- 拟饵专属的 9 个 float 字段（`bbhhojphpfa` / `dlphncpeied` / `edfipbganca` 等）
  全是物理参数，值是 IEEE754 float 的整数位表示（`1073741824` = 2.0f），
  与分类无关。

### 2.1 baitType=8 怎么区分「下沉」与「Pop-up」

用户指出的关键点。判定依据是 `brand`：

- `brand` 含 `_pp_` 或 `pp_` 段 → **Pop-up**，222 款；
- 否则 → **下沉**，356 款。

全量验证：578 款按 `brand` 判定，与名称里的 `PopUp`/`Pop-Ups`/`Pop Ups`
标记 **578/578 完全吻合，零例外**。

样本对照（香子兰同口味跨形态）：

```
boils_hvz_van12       香子兰 12           brand=hvz_boils_van        → 下沉
boils_hvz_van_pu12    香子兰 Pop-Ups 12   brand=hvz_boils_pp_van     → Pop-up
boils_op_van14        香子兰 14           brand=op_boils_van         → 下沉
boils_op_van_pu14     香子兰 Pop-Up 14    brand=op_boils_pp_vanila   → Pop-up
```

同款饵的两个形态在库里是**两条独立 item**，钓组用法不同，不能合并。

### 2.2 baitType=1（自然的）里多出来的 7 款

用户观察到「游戏里自然的下面只有 14 款」，而库里是 21 款。多出来的 7 款：

| item_id | 名称 | 商店 | 配方 |
|---|---|---:|---:|
| `boil_brown` | 棕色香煮成饵 | 0 | 0 |
| `boil_green` | 绿色香煮成饵 | 0 | 0 |
| `boil_orange` | 橙色香煮成饵 | 0 | 0 |
| `boil_red` | 红色香煮成饵 | 0 | 0 |
| `boil_rose` | 粉色香煮成饵 | 0 | 0 |
| `boil_yellow` | 黄色香煮成饵 | 0 | 0 |
| `sunflower_cake` | 榨饼 | 0 | 0 |

全库追踪：这 7 款**只出现在 `item_catalog` 与 `item_def` 两张表**，
`shop_item` / `recipe` / `loc_bait` / `fish_bait_pref` / `companion_bait_fish`
全部零引用。即「游戏里不可见、不可获得」的遗留数据。

**结论**：规则编辑器里应当排除这 7 款，或单独标注「未启用」。
其余 14 款均有商店或在售配方。这正好对上用户看到的 14 款。

### 2.3 一束藻类的位置

`一束藻类` → `baitType=1` → 游戏菜单「鱼饵 › 自然的」。

用户原话：「如果用户只选择了这个，说明当前鱼种只吃自然类下面的这一项」。
即规则里写 `一束藻类` = 只匹配这一个 item，不展开成整个「自然的」类。
这与现有 `matchOne` 的单饵命中行为一致，无需改动匹配逻辑。

### 3.1 「旋转饵」为什么不是第 21 类

菜单里「旋转亮片路亚」与「旋转饵」并列，容易误判成两个 `lureType`。实际数据：

| 名称 | brand | kind | lureType |
|---|---|---|---:|
| 旋转亮片#1 01…09 | `pom_vertushka1` | pomor | 1 |
| 旋转饵1号 001…006 | `n1spin_lure` | Handmade | 1 |
| 旋转饵3号 001…006 | `n3spin_lure` | Handmade | 1 |

三者全是 `lureType=1`。也就是说「旋转饵」是**旋转亮片路亚这个菜单项下的产品系列**，
正好落在层级选择器的第三层（brand），不该另立一个类型。

同理 `lureType=20` 的 56 款是 `Vibra Colorado` / `Brilliance Colorado` 这类
带 Colorado / Double Willow 叶片的 spinnerbait，在菜单里对应「旋转饵」这一项，
不是「旋转亮片」。

**层级结构（数据直出，非自造）：**

```
拟饵(cat17)
  └ lureType 20 类（游戏菜单原文，一一对应）
      └ 品牌（item_def.kind，28 个）
          └ 型号组（名称去规格号，430 个）
              └ 具体规格/颜色/品质（3178 款）
```

天然饵同理，但天然饵的 `kind` 基本为空（非品牌饵），所以天然饵是三层：

```
鱼饵(cat27)
  └ baitType 16 类（游戏菜单原文）
      └ 型号组（392 个）
          └ 具体规格（945 款）
```

### 3.2 同一商品名的多行是品质分档，不是重复数据

`item_def` 里一个中文名常对应 2~3 个 `item_id`：

```
hm_spinner_n1_bl_hq  → 旋转饵１号　004   (high quality)
hm_spinner_n1_bl_mq  → 旋转饵１号　004   (medium)
hm_spinner_n1_bl_lq  → 旋转饵１号　004   (low)
```

**这不是脏数据**，是同一款饵的品质档位（`_hq` / `_mq` / `_lq` 后缀）。
对层级选择器的直接影响：

- 型号组必须按**名称**折叠，不能按 `item_id` 数，否则 3 个品质档会被算成 3 个规格；
- 写型号名进规则时，三个品质档必须**一起命中**——这是 `TestModelNameMatchesAllSpecs`
  的核心断言（566 个型号组全部覆盖）。

这两处已经是落地验证过的写法，沿用即可，但要做以下修正：

## 5. 型号名写进规则却零命中（已修）

这是本轮重构里最有价值的一个发现，因为它属于**静默失效**：后台点得动、抽查签按型号分组、
判鱼一条都不认，界面上没有任何报错。

### 5.1 现象

后台层级选择器的第三层是「型号」（`Spiker #2`、`Baby Craw 3.5`），点一下写进规则的是
型号名而不是完整商品名。用户心智是「该型号所有规格都吃」。实测 873 个型号组：

| 阶段 | 型号名命中全部规格 | 占比 |
|---|---:|---:|
| 修复前 | 836 / 873 | 95.8% |
| 修复后 | 872 / 873 | 99.9% |

失败样例：`Salmon T1 Crank 10` 0/13、`Baby Craw 2.5` 0/11、`Spiker #2` 9/18。
注意最后一个是**半失效**——部分规格命中、部分不命中，比全失效更难发现。

### 5.2 根因（两个叠加）

**根因 1：`isZeroPaddedIndex` 把最常见的规格号否掉了。**

```go
// 错：次位必须是 1-9
if rest[1] == '0' { return false }
```

`001`、`002` 的次位恰恰是 `0`，于是标准补零编号全部被判成「不是规格号」。
真正要排除的只有 `000`（`Hunter 1000` 的尾巴，属产品名）。

**根因 2：`matchOne` 在型号名以数字结尾时直接放弃。**

`Baby Craw 3.5`、`Salmon T1 Crank 10` 都以数字结尾。原逻辑要求「规则词末字符非数字
才接受后续数字」，于是这类型号无论怎么写都落空。

### 5.3 修复

1. `isZeroPaddedIndex` 改为「以 `0` 开头 + 至少含一个非零数字」；
2. `matchOne` 增加一条判据：规则词等于 `baitBaseName(商品名)` 时直接命中。
   **必须复用 `baitBaseName`**，否则后台的型号分组、自动轮换分组、判鱼命中范围
   会各用一把尺子；
3. `baitSpecTail` 的分隔符字符集补上 `#`：一批海钓饵把规格写成
   `Stor Fisk L33-450 #1`，不补 `#` 会剥成 `Stor Fisk L33-450 #`，
   留下孤立井号当型号名（162 款受影响）。

### 5.4 守卫

`internal/gameserver/bait_model_name_test.go`：

| 测试 | 守什么 |
|---|---|
| `TestModelNameMatchesAllSpecs` | 566 个型号组，组名必须命中该组全部规格（含 `_hq/_mq/_lq` 品质档） |
| `TestModelNameZeroPaddedIndex` | `001`/`012` 是规格号，`000`/`00` 不是 |
| `TestModelNameCoversSpecVariants` | 补零 / 小数点 / 连字符 / NBSP / `#序号` 五种写法；反向检查不吞别的产品 |
| `TestBaitBaseNameStable` | 单层剥离结果，且剥出的名字不能以分隔符收尾 |

> 注意「只剥一层」是设计不是 bug：`Salmon T1 Crank 10 001` 剥一层得
> `Salmon T1 Crank 10`，再剥就把型号号 10 也吃了，5/10/15 三个型号会并成一组。
> 因此该测试**不测幂等**。

### 5.5 唯一剩余的 1 组

`虾` —— 它同时是拟饵 `lureType=15` 的整类词。整类词优先按枚举解析，

## 8. 同名型号跨类别（`颗粒@鱼子`）与编辑器三项改造

用户在真实使用中报了三件事，三件都指向同一处「界面能选、规则表达不了」的缝隙。

### 8.1 现象：加了「颗粒的鱼子」以后，「香煮成饵的鱼子」加不进去

截图里的操作是：白化鲃鱼的「吃」列表已经有 `鱼子`，再从层级选择器里挑
香煮成饵 → 鱼子，点加入，没有反应。

两层原因，都得修：

1. **前端按名字去重**。旧 `brPickAdd` 是
   `if(list&&!list.includes(name))list.push(name)`——键是名称字符串。
   「颗粒的鱼子」写进去的是 `鱼子`，于是「香煮成饵的鱼子」判成重复，静默跳过。
2. **规则语法表达不了类别**。实测 `鱼子` 这一个词命中 **14 款**，横跨 4 个类别：

   | baitType | 类别 | 款数 | 具体 |
   |---|---|---|---|
   | 1 | 自然的 | 1 | `caviar` |
   | 8 | 香煮成饵 | 8 | `鱼子10/16/20/26` + `鱼子 Pop Ups 10/16/20/26` |
   | 9 | 颗粒 | 3 | `鱼子 14/18/24` |
   | 10 | 人造玉米 | 2 | `鱼子 红色` / `鱼子 黄色` |

   所以就算绕过界面去重，写一个 `鱼子` 也会把另外 3 个类别一起放行，
   无法表达「只要香煮成饵的鱼子」。

**这不是孤例。** 全库 4123 款饵里，**25 个型号名横跨 ≥2 个二级类别**：

```
香子兰      → 香煮成饵(6) / 颗粒(4) / 人造玉米(1)
鱼子        → 自然的(1) / 香煮成饵(4) / 颗粒(3)      ← 另 4 款名称带后缀
红虫        → 幼虫(1) / 香煮成饵(2)
红蚯蚓      → 蠕虫(1) / 香煮成饵(3)
老虎坚果    → 坚果(1) / 香煮成饵(4)
大蒜        → 人造玉米(1) / 颗粒(4)
…（共 25 个，见 TestZZScopeProbe 的输出，该探针已在修复后删除）
```

### 8.2 修法：新增「类别限定词」语法 `限定词@饵名`

选 `@` 作分隔符的依据是实测：4123 个饵的官方名里 `@`、`>`、`｜`、`·`
出现次数都是 **0**（`'`、`"`、`` ` ``、`\`、`&`、`<`、`>` 也是 0）。
这类字符一旦出现在饵名里，内联进 `onclick="fn('…')"` 会截断 JS 字符串，
整屏按钮静默失效——所以既要用它当分隔符，也得顺手确认它不会出现在数据里。

判定逻辑（`fishing_bait_rules.go`）：

```go
// splitBaitScope 拆 `限定词@饵名`：ok=false 表示这只是一个普通饵名。
// 必须**双向**都成立才认作限定：
//   1. `@` 左边能解析成一个类别词（baitTypeTerms）；
//   2. `@` 右边非空。
// 只判「含 @」是不够的：饵名里原则上可能出现 @（现在是 0 款，但以后可能变），
// 那样会被误拆成「限定词不存在 → 匹配失败 → 原本能吃的饵变不吃」。
func splitBaitScope(term string) (scope BaitTypeTerm, name string, ok bool)
```

匹配时**两道都要过**（`ruleBait.matches` 与 `matchesPreNorm` 两条路径都改）：

```go
if scope, name, ok := splitBaitScope(term); ok {
    if !scope.matches(b) {          // ① 属于该类
        return false
    }
    return b.matchOne(name, ...)    // ② 名字匹配（含型号名/base 全部既有规则）
}
```

只判类别会把同类的全部颗粒放行；只判名字等于没写限定。两条都是静默失效，
所以 `TestBaitScopeNarrowsSameNameAcrossCategories` 里各有一条反向守卫。

`matchTerms` 为此新增 `scopeIdx / nameRaw / nameT / nameKT` 四个平行数组。
`nameRaw` 不能省：`matchOne` 的第一个参数要跟型号名做精确比较，
把归一化后的 `nameT` 传进去会让「带空格/连字符的型号名」判不出来。

**批量与单条必须同口径**：`TestBaitScopePreMatchesSameAsDirect` 逐款比对
`matches()` 与 `matchesPre()` 的结果。这两个路径历史上写过不同的 bug，
表现是「后台抽查签能抽到、判鱼拒收」这种只在一半场景出现的静默失效。

### 8.3 后台接口：只给「真的重名」的型号补限定

`GET /api/bait/categories` 的型号行新增两个字段：

```jsonc
{ "base": "鱼子", "term": "鱼子",
  "scope_term": "颗粒@鱼子",             // 跨类别同名时才有
  "shared_with": ["香煮成饵"] }          // 同名的其它类别（类别词，不是 label）
```

- **只有一个类别含该名时 `scope_term` 留空**，前端继续用短写法。
  否则 566 个型号组全变成「类别@名」，规则表没法读。
  `TestBaitCategoriesScopeForSameNameAcrossCategories` 有一条反向断言守着。
- `shared_with` 放**类别规则词**而不是分类树 label：label 是
  「香煮成饵（下沉 + Pop-up）」，写进提示里既长、又和 `scope_term` 前缀对不上，
  用户会以为是两个不同的东西。

### 8.4 编辑器三项改造

| 要求 | 改法 |
|---|---|
| 编辑框太小 | `showModal(..., wide=true)` → `.modal.wide` 用 `min(1180px,97vw)`；`.br-layer>.v` 的 `max-height` 150→190px、规格列表 190→230px；标题 19px |
| 支持多选 | 点击只切换 `BR_PICK.picked`（暂存区），底部常驻工具条显示「已勾选 N 项」+「一次性加入」；弹窗不再自动关闭 |
| 同名加不进 | 型号按钮带「同名×N」徽标；写进规则用 `scope_term`；标签显示拆成「颗粒 › 鱼子」 |

交互上有一个必须说清的取舍：**同一个按钮要承担两种操作**。
`renderBrPicker` 里每个选项左边有一个小圆点（`.tick`）：

- 点圆点 → `brPickToggle()`，勾进暂存区（`event.stopPropagation()` 阻止冒泡）；
- 点按钮其它位置 → `brPickSet()`，把收束范围收到这一层。

不这么拆，用户就只能二选一：要么能往下钻、要么能多选。三层（二级类型 /
形态 / 型号）都按这个方式挂圆点。

**两种「已加入」状态必须视觉可分**，否则用户不知道关掉弹窗会不会丢：

- `已在列表`（绿）＝ 保存后生效的，在 `brBucket` 里；
- `已选`（蓝 + 左侧色条）＝ 只是暂存，关掉弹窗就没了。

// 跨类别同名的型号例外——那种情况下这一行是唯一能看到「同名×N」与

## 9. 全库统一为 `类别@饵名`（2026-11-25 二次落地）

用户要求把「类型@鱼饵」定为唯一书写格式，已配置规则全部重写一遍。原文五条：

1. 统一格式为 `类型@鱼饵`，库里已配好的一并更新；
2. 带具体口味 + 规格号的放宽到同口味基名（`螃蟹和贻贝 可溶 15` → `香煮成饵@螃蟹和贻贝 可溶`）；
3. 一个名字涉及多个类别时，把涉及的类别全部列出；
4. 已写整类词（如 `亮片类`）又追加具体型号的，收窄到具体型号；
5. 旧「旋转饵」改用新类型名「旋转亮片路亚」。

### 9.1 改写器口径（已删除，结论留档）

本轮用一次性改造器跑全库，`改动 2207 处，放宽 506 处，死词 0，丢命中 0`。
逐鱼验收「改写前能吃哪些饵 vs 改写后能吃哪些饵」得 **`丢 0 款（0 鱼）；增 2168 款（156 鱼）`**。

名字选择优先级**不能反**：

```
唯一真实型号名  >  剥规格号  >  保留原词（口味族前缀）
```

写成「剥规格号优先」会让 `Stor Fisk M25-600 #8` 多剥一层变成 `Stor Fisk M25`，
把 M25-300 / M25-450 一起放行——实测让「剑鱼」从 9 款涨到 96 款。改回正确顺序后
新增从 4124 款降到 2168 款。

`baitSpecTail` 只剥一层规格号，是硬约束：`(?:[-_\s\x{00a0}\x{3000}#]*\d+)$`。

### 9.2 本轮发现并修掉的真缺陷：`带毛汲钩(jig)` 的括号截断

规则词 `带毛汲钩(jig)` 写进 `fishing_bait_rules.txt` 后，解析器把第一个 `(` 之后
的全部内容当作「不吃 / 底钓只吃」限定段，其后条目整段截断，**14 条鱼的 27 款饵静默丢失**。

实测客户端 `kLureTypeHairyJig` 的简中原名是「带毛汲钩」，**没有 `(jig)`**，括号是早期代码自造。
正式名已去掉括号，`带毛汲钩(jig)` 降为 Alias 只为兼容历史后台数据。
这条约束现在写进 `TestBaitScopeTermsNeverContainSeparator` 的姊妹规则：**类别词也不许含 `(`**。

### 9.3 副产物：`groundbaitAcceptedFamilies` 必须按 `@` 后的名字判族

改格式后 `TestGroundbaitRuntimeAffinityMatchesOfflineProbe` 立刻变红。根因不是数据错，
而是族归属函数拿**整条规则词**做关键词匹配，类别词本身带语义：

- `香煮成饵@红虫` 同时命中类别词「香煮成饵」（boilie）与名字「红虫」（worm）；
- 只吃虫的鱼凭空多出一个 boilie 认可，该族加权从 0.85/0.50 抬到 1.00；
- 结果「犬首鮈」「三刺鱼」被挤出预烘亲和表（4 行消失）。

改为按 `@` 后的名字判族后，行数与旧表**完全一致**（1013 行，新增 0 / 删除 0），
剩 22 行 0.006~0.014 的小幅漂移，成因是新写法显式列出了
`香煮成饵@贻贝和水果` 这类条目、比旧合并词多一个 plant 族——属格式细化的正常结果。
已用 `TestRebakeGroundbaitAffinity -args -apply` 重烘写回（`profile_version=7`）。

库里 2 行覆盖记录仍是旧格式，已改写并用**真实库 4123 款饵**实测新旧命中集合等价：

| 鱼 | 改写前后命中 | 结果 |
|---|---|---|

### 9.5 本轮确认「看似残留、其实是原名」的三类词

- **口味族后缀词**（`椰子类`/`玉米类`/`大蒜类`/`鱿鱼类`/`自然风味`）是口味族前缀，
  不是型号名；换成任一具体型号会丢掉同族其它成员，故保留原词。
- **真实型号名可以带「类」**：`一束藻类`、`什锦水果类`、`椰子和奶油类` 都是客户端原名。
  实测把这些 `类` 去掉后命中集合完全相同，说明它们不是自造后缀。
- **`亮片类` 是历史合并词**（651 款 = 旋转亮片路亚 296 + 勺子路亚 355），
  本身不是任何真实饵名前缀，已按要求拆成两个正式类别词。
- **`旋转饵` 与 `旋转亮片路亚` 是两个不同类型**：`kLureTypeSpinner`（lureType=1，296 款）
  才是「旋转亮片路亚」；`kLureTypeSpinnerBait`（lureType=20，56 款）才是「旋转饵」。
  旧标记 `旋转饵类`（lureType=1）改正式名，`旋转饵`（lureType=20）保持不动。
