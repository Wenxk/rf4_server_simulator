## 一、测试方法与口径

### 1.1 为什么不枚举「饵 × 鱼」

朴素做法是 18 图 × 4 季 × 24 时 × 3 层 × 4123 饵 ≈ 5.78 亿次判鱼，不可行。
判鱼链每一层都是**乘性**的，任一层为 0 即该候选出局，且各层之间没有「补救」关系：

| 层 | 生产函数 | 依赖 | 能否归零 |
|---|---|---|---|
| L1 饵料 allow | `filterFishBaitSet` | (地图, 鱼种, 饵池) | **能**（`best<=0` 时剔除） |
| L2 水层地板 | `applyBiteGates` | (鱼种, 钓层) | 仅当 `layerFloor<=0` |
| L3 昼夜禁口 | `fishBiteEnvironmentWeight` | (鱼种, 时段) | **能**（曲线 <0.5 直接返回 0） |
| L4 适温/季节/天气 | 同上 | (鱼种, 水层, 季节, 时段) | **不能**（因子有下限，末段 `clamp(.08,2.5)`） |
| L5 鱼群分布 | `distributionMultiplier` | (鱼种, 区域, 4 游戏小时周期) | **能**（`v<0.3` 返回 0） |

于是「该组合至少有一种鱼可钓」等价于「存在鱼 f 使五层系数全为正」。
L1 用生产函数**一次传入全部 4123 款饵**——`filterFishBaitSet` 内部就是 `for 饵取 max`，
返回的正是「至少一款饵可用」的鱼种集合，与逐饵枚举在数学上完全等价。

### 1.2 季节代表日必须反解，不能写日历

`SeasonDay = ((now − 1438387200) / 3600) % 365`，而 **1 真实小时 = 1 游戏日**，
所以整个季节周期只有 **365 真实小时 ≈ 15.2 真实日**，不是一年。

第一版按「4 月 15 日 = 春」构造，实测落在**冬**。改为反解 `seasonDay`：

```
u = SeasonEpochUnix + k·(365×3600) + mid×3600,  遍历 k 取最小 u ≥ anchor
```

`seasonMids` = 春 100 / 夏 195 / 秋 285 / 冬 20。四个季节均通过 `fishSeasonAt` 回读校验。

### 1.3 分布层必须对多钓点取并集

`fishArea` 把世界切成 40 单位一格，`distributionMultiplier` 每 4 游戏小时重抽。
**同一时刻不同钓点的存活集合差别极大**——实测同一张图同一时刻，10 种鱼在 10 个钓点间
存活 3~9 种。只采样 `spot=0` 会同时高估与低估风险（玩家会走动，某格空了不代表该图该时段无鱼）。

因此对同一 (地图, 季节, 时段, 钓法, 水层) 扫 **16 个探针钓点**取并集：
「存在某个钓点能钓到该鱼」即算该鱼可钓。

### 1.4 天气必须按 slug 取，且取完整结构

这一条是本次测试**最重要的一次自我修正**，见第四节。

## 四、一个必须交代的自我修正（测试自身缺陷）

第一版跑出来的数据是**错的**，18 张图水温完全相同（5.18–19.29），
根源是三个口径问题叠在一起。已全部修正并重跑，本报告用的是修正后的数据。

### 4.1 天气按中文名查，永远查不到

`loadAllMaps` 从 `loc_alias` 取 `(alias, loc)`，`loc` 是**中文名**。
测试把 `m.Loc`（中文名）传给 `WeatherPreviewForMap`，而该函数以
`map_defs.json` 的 `level_*` key 索引 → 永久 `ok=false` → 天气层静默降级成「未知」。

后果：`fishWaterConditionsFor` 回落到 `seasonalAir`（与地图无关的四季常数
`{10,23,13,1}`），于是 18 张图算出完全相同的水温，「季节温度区间」这一维度实际失效。

**修正**：改用 slug（`m.Alias`）。修正后水温跨度从 5.18–19.29 扩展到 1.63–28.18。

### 4.2 只填 airTemp，天气其余字段全为零值

生产 `Session.weatherAt` 返回的是**完整** `fishingWeather`（气温 + 前一小时气温 +
风 + 雾 + 天气类型）。第一版只填了 `airTemp`，导致：
`fishWeatherKindWeight` 拿到 `kind=0`、`fishWeatherExtraWeight` 拿到零值风/雾、
清澈度计算里 `cloud/rain/fog` 全为 0 → 判鱼输入与线上不是同一套。

**修正**：按 `WeatherPreviewHour` 补齐 `previousAirTemp`、`wind`（km/h ÷ 3.6 → m/s）、
`fog`、`kind`。

### 4.3 水层维度确实不产生「零」

修正后 `after_diel` 仍**完全不随水层变化**（1728/1728 时段一致）。这不是 bug：

- `fishLayerWeightProfile` 的区间外分支有 `max(.02, ...)` 下限
- `fishBiteEnvironmentWeight` 每个因子有 `floor=.25`（首因子 `.05`），末段 `clamp(factor,.08,2.5)`
- 温度是高斯响应 `.35+.65·exp(−.5z²)`，**永不为 0**

实测 7 个钓法-水层组合的最小权重都在 **0.1055–0.4039**，全部 >0。
所以在「存在性」口径下，**水层与温度只影响中签概率，不影响可钓性**。
真正能把候选归零的只有：L1 饵料 allow、L2 水层地板（仅当 `layerFloor<=0`）、
L3 昼夜禁口、L5 鱼群分布。

> 这条结论与第一阶段的「超层概率」并不冲突：第一阶段问的是**已被抽中的鱼里**
> 有多大比例超出活跃水层，那是概率分布的尾部质量；这里问的是**还有没有候选**，
> 那是存在性。前者可以很大，后者依然成立。

## 五、可钓性口径与第一阶段的一致性说明

第一阶段报告（`analysis-layer-floor-probability-2026-11-25.md`）记录了
「浮钓·面包·浅水 100% 超层」——那是因为面包的 allow 只有 3 种鱼
（`c.carp`/`c.roach`/`crucian`），三者 `LayerMin` 全 ≥0.52，浅水 0.16 够不到。

**本轮不会把这种情况表现成死时段**，因为本轮是「**任意饵**」口径：
`filterFishBaitSet` 一次传全部 4123 款饵，只要该鱼有一款合法饵就算过。
面包够不到浅水层，但红虫能——于是「该图该时段是否可钓」仍为真。

两个结论并不矛盾，它们回答的是两个不同问题：

| | 第一阶段 | 本轮 |
|---|---|---|
| 问题 | 已上钩的鱼里，超层占比多高？ | 还有没有鱼可钓？ |
| 口径 | 单一饵（面包/红虫/亮片） | 任意饵（4123 款取并集） |
| 结果 | 面包·浅水 100% 被迫超层 | 12,096/12,096 均可钓 |

**玩家实际遇到「面包在浅水空军」是真实的**，但那是「这款饵在这个水层无效」，
不是「这张图这个时段没鱼」。若要按单饵口径评估死时段，需另跑一轮
「每款饵 × 每图 × 每时段」的测试。

## 六、可信度排查

为排除「假阳性」（测试写错导致恒为可钓），做了以下核对：

| 检查项 | 结果 | 含义 |
|---|---|---|
| `bait_out` 淘汰总人次 | **0** | 全饵池下每种鱼至少有一款合法饵 |
| 鱼种规则覆盖 | 252 / 253 有种规则 | 仅 1 种无规则（走 companion 证据兜底） |
| `after_bait == roster` | 12,096 / 12,096（100%） | allow 层在全饵池下不淘汰 |
| `after_all < roster` | 12,096 / 12,096（100%） | **后续层确实在过滤，非恒真** |
| `diel_out` 淘汰人次 | 109,956 | 昼夜禁口大量生效 |
| `dist_out` 淘汰人次 | 89,516 | 鱼群分布大量生效 |
| `env_out`（w<0.05） | **0** | 温度/水层从不把权重压到 0.05 以下 |
| 单层清空候选的 cell 数 | **0** | 从未出现某一层单独把候选清零 |
| `after_all` 分布 | 2 ~ 45（中位 16） | 有真实梯度，非全图恒等 |

`after_all < roster` 100% 说明过滤链在工作；`after_all` 跨度 2~45 说明结果随条件变化。
这两条合起来排除了「恒真」的可能。

**零重叠的成因**（`diel_out ∩ dist_out = 0`）：判鱼链是**短路顺序**执行
（昼夜禁口先于分布），被禁口的鱼不再进分布层统计。这是记录口径，不是数据异常。

## 八、供后续决策的三条观察

本次不改配置，仅记录现象供「活跃水层区间调整」时参考。

1. **晨段（5–8 时）是全时段最薄弱环节**：平均可钓数只有夜段的 53%（11.0 vs 21.0），
   且 18 张图里最小值有 14 张出现在晨段。旧奥斯特罗格湖冬季晨段只剩 2 种（`c.roach`/`sig_ostr`）。
   这不属于异常（仍有鱼），但若继续收窄活跃水层，**晨段会最先触底**。

2. **水层与温度在存在性口径下不构成约束**：因子下限（0.05/0.25）与末段 `clamp(.08,2.5)`
   保证了它们永不为 0。也就是说，即使某鱼活跃水层被收窄到很窄，玩家仍能钓到它
   （只是概率极低）。若希望「超层彻底钓不到」，需要把 `bite_gate_layer_floor`
   （水层地板，当前缺失走默认 0.01）设为 0，而不是靠收窄区间。

3. **「全水层」鱼种设置不会改善晨段**：晨段变窄的成因是昼夜禁口曲线
   （`fish_diel_inactive_block`，当前 1，曲线 <0.5 整段禁口），与活跃水层无关。
   把部分鱼种设为全水层能降低「超层捕获」争议，但对晨段可钓数几乎没有帮助。
